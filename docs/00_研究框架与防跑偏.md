# 00 研究框架与防跑偏（最高优先）

> **这是整套工作流里优先级最高的一条。** 所有 agent（包括总览）开工先读本项目的研究框架文件；任何决策、任务单、消息和它冲突时，以研究框架为准，停下报总览。

AI 做研究时会想偏、查错、读错文章，而且自己往往看不出来。放手让它一路做下去，错会一层层叠起来，有时越改问题越大。

对策只有一个核心：**先把研究问题和主要方法路线定死，写进一个文件，冻结；之后所有工作都在这个框架里做，框架的改动必须经过你严格审核。** 再配上定期的跑偏检查，看实际做的事有没有偏离这个文件。

## 1. 一个文件：研究框架

- 位置：研究仓库 `docs/overview/research_frame.md`（研究仓库是私有的）。模板：[research_frame.md](../templates/repo/research_frame.md)。
- 内容：研究问题、研究对象、不做什么、可证伪的假设和"什么结果算不成立"、贡献的上限、**主要方法路线**（每条路线的主实验和止损条件）、证据要到什么程度。
- 不放：查新结论、创新点论证、标题措辞，这些仍放私有工作区。
- 时点：选题准入通过之后、**任何正式实验之前**写好。独立审查一次，你严格审，批准后冻结：状态改为"已冻结"，记 sha256 和你的批准原话。
- 冻结后只有一种改法：出新版本（§4）。旧版本留在 Git 历史里，改动记录写在文件末尾。

## 2. 三层，各自谁能改

| 层 | 内容 | 在研究框架里吗 | 能不能改 | 谁批 |
|---|---|---|---|---|
| **问题** | 研究问题、对象、假设、不成立的标准、贡献上限 | 在 | 原则上不改；真要改，等于开新项目 | **你，严格审** |
| **主线** | 主要方法路线、主实验、判定线、止损条件 | 在 | 只有止损条件触发后才能改 | **你，严格审** |
| **分支** | 次要实验、实现细节、图、措辞、排期 | 不在 | 总览和 agent 自己定 | 你定期抽查 |

## 3. 五条硬规矩

### 3.1 问题不跟着结果改

- 不根据做出来的东西修改研究问题。
- 结论可以随证据**缩小**：负结果照实报告、措辞收窄、某项贡献降级。
- 结论不能**换靶子**。判断方法：拿新结论问一句"研究框架里有没有一句话是在问这个？"没有，就是换靶子，按改问题处理。

### 3.2 每条主线事先写好止损条件

- 研究框架里每条主线都写：做到什么程度、看到什么结果，算这条路走不通。要具体到能判断的结果，不写"效果不好"。
- 止损条件触发 → agent **停下**，写主线改动申请（[模板](../templates/repo/mainline_change_request.md)）交总览，总览交你。agent 和总览都不能自己换一条路接着做。
- 没有事先写好的止损条件，"行不通"就会被 AI 解释成"再改改就行"。

### 3.3 同一个问题最多修两次

- 一个 bug、一个对不上的数字、一个跑不通的实验，修两次还没解决，就停下报总览。agent 在 STATE.md 的"反复修补"一节记次数。
- 总览判断：只碰分支，就换思路或放弃这个分支；碰到主线，按 §4 走。

### 3.4 做事的 AI 不审自己

AI 的错大多是它自己看不出来的。在同一个对话里让它检查，它往往只会把原来的推理再走一遍。

- 下面这些节点由**没参与过的新对话**审（[独立审查提示词](../templates/prompts/independent_audit.md)）：
  - 研究框架定稿前；
  - 主线改动申请交给你之前；
  - 要发给别人的东西（给导师和评审的材料、论文初稿）发出之前；
  - 出现"好得意外"的结果时。
- 给审查者的只有原始材料和要审的结论，**不给推理过程和对话记录**。
- 审查意见由总览逐条回应：改、不改（写理由）、待查。

### 3.5 事实要能查到出处

- **文献**：说"某论文做了 X"，附论文、章节、原句和读取深度（摘要 / 全文）。读不到原文写"未核实"，不能当事实用。检索失败不等于"没有先例"。
- **数字**：只从代码和结果文件来，不在文字里算。对外文档里的每个数字都能指到一个文件。
- **做法**：转述实验怎么做的，回到预注册或报告原文核对，不凭记忆。
- **状态**：项目进度、同步、任务状态以日志和文件为准，不照抄旧记录。

## 4. 改研究框架的流程

| 改动碰到 | 流程 |
|---|---|
| 问题 | 写改动申请 → 独立审查 → 你严格审 → 批准后视同新项目：重新过选题准入，研究框架出新的大版本 |
| 主线 | 止损条件触发（或总览判断需要）→ 写主线改动申请 → 独立审查 → 你严格审 → 批准后总览出新版本、记 sha256、写决策 |
| 分支 | 总览直接决定、写决策；跑偏检查报告里列出来 |

**每次决策前的四问**（总览写决策、巡检处理消息时都要问）：

1. 这件事改不改研究问题或研究对象？
2. 改不改研究框架里的主线、主实验或判定线？
3. 有没有提出研究框架没覆盖的新结论？
4. 是不是某条主线的止损条件已经触发了？

任何一个答"是"，就不是例行事项：总览不能直接决定，巡检只能排队给你。决策记录里写明层级和四问的答案。

## 5. 定期跑偏检查

研究框架冻结之后，定期拿实际做的事和它比一次，看有没有越跑越偏。

- **谁来比**：一个没参与过的 AI（[跑偏检查提示词](../templates/prompts/drift_check.md)），可以建成每周一次的云端定时任务，也可以你开一个新对话手动跑。它只读，不改任何文件，只写一份报告到 `reports/drift/YYYY-MM-DD.md`。
- **比什么**：
  1. 最近的决策、任务单、报告、对外材料，有没有改研究问题或对象、有没有新结论、有没有主线被悄悄换掉；
  2. 各主线离止损条件还有多远，有没有已经触发却没上报的；
  3. 分支有没有长成主线（花的预算、篇幅、在论文里的分量）；
  4. 抽三到五个事实（文献说法、数字、做法），回原文核对。
- **结果怎么用**：报告给出"没有偏 / 有偏的迹象 / 已经偏了"。后两种由总览写进你的待办，附具体位置。
- **你自己**：建议每两周花半小时，读研究框架和最近一份跑偏检查报告，看结论你同不同意。

## 6. 你的精力花在哪

1. **研究框架**：立项时审一次，最值得花时间。问题定错了，后面做得再好也没用。
2. **主线改动申请**：止损条件是不是真的触发了、证据对不对、换的路线是不是还在回答原问题。
3. **跑偏检查报告**：定期看一眼结论，有疑问再深挖。
4. **好得意外的结果**：AI 的错经常表现为结果太干净、太顺。
5. **要发给别人的东西**：事实和数字。

分支：看跑偏检查报告里列出的变动，随手抽查一两项。

## 7. 常见的跑偏方式

这些都在实际项目里出现过，包括总览自己犯的。

| 现象 | 怎么发生的 | 哪条规矩防它 |
|---|---|---|
| 给别人的总结里把实验做法写错（例如校准用的是哪批样本、某个距离比的是什么和什么） | 凭印象转述，没回到预注册和报告原文 | 3.5、3.4 |
| 把一个有混杂因素的现象说成某个已知效应 | 只看了差值，没想还有什么别的解释 | 3.4 |
| 引用了一篇查不到原文的论文 | 二手转述当成事实 | 3.5 |
| 定时巡检连续几天照着旧记录报一个已经解决的问题 | 状态只记了"出事"，没记"已恢复"；后来的运行照抄 | 3.5 |
| 一个效果不好的模块，换个说法继续当贡献 | 看了结果之后重新解释贡献 | 3.1 |
| 一条路走不通，agent 自己换了条路接着做，几轮以后已经不在回答原问题 | 没有止损条件，也没有上报的规矩 | 3.2、§5 |
| 修一个对不上的数字，越改牵扯的文件越多 | 没有修补次数上限 | 3.3 |
| 参考文件让照着版式做，AI 连内容结构也照搬了 | 没分清"参考什么" | 拿不准先问；内容结构以研究框架为准 |

## 8. 和其他关卡的关系

顺序：选题准入 → **研究框架（你审、冻结）** → 各实验预注册 → 执行 → 定期跑偏检查 + 关键节点独立审查 → 投稿审核。

| 关卡 | 管什么 | 文档 |
|---|---|---|
| 选题准入 | 这个想法值不值得做 | [10](10_选题准入与投稿审核.md) §1 |
| **研究框架** | 做什么、怎么做、什么时候算走不通；之后不能随意改 | 本文 |
| 实验预注册 | 单个实验的做法和判定线，看数据前写死 | 各项目的预注册文档 |
| 跑偏检查 / 独立审查 | 实际做的事有没有偏离框架；关键节点的事实和推理 | 本文 §5、§3.4 |
| 投稿审核 | 投哪里、够不够格 | [10](10_选题准入与投稿审核.md) §2 |
