# 02 角色设计

## 1. 六种角色

| 角色 | 怎么运行 | 读写什么 | 什么时候需要 |
|---|---|---|---|
| **项目总览**（交互） | 你常开的一个对话 | 决策、任务单、`需要你处理.md`、你的桌面待办 | **必须**，一个项目一个 |
| **总览巡检**（定时） | 定时任务，每 2 小时 | 同上；只做例行决定，大事排队给你 | 建议有：你不在时也能回复 agent |
| **云端执行 agent** | 定时任务，在云端跑，通过 GitHub 读写仓库 | 自己负责的代码、文档、`reports/<自己>/` | 每条主要工作线一个 |
| **本机执行 agent** | 定时任务，在你电脑上跑 | 同上，外加只在本机的数据（不进 Git 的文件、需要本机密钥的 API 调用等） | 某条线依赖本机文件时 |
| **交互式 agent** | 普通对话，你在场时用 | 同上 | 需要你同时动手的工作：真机实验、现场调试 |
| **远端执行端** | 服务器 / 超算上的 Claude Code，你说一句固定的话它才动 | 只按编号指示执行，只提交自己的汇报 | 计算在服务器上跑、而其他 agent 登录不了服务器时 |

另有**按需 agent**（查新、写论文、做图……）：任务明确、做完就撤，不必常驻。

## 2. 定几个 agent

原则：**按"工作线"分，不按"任务"分**。一条工作线 = 有自己的代码目录、自己的产出、能独立推进几周。

| 项目规模 | 建议配置 |
|---|---|
| 小（1 条主线） | 总览 + 1 个执行 agent。巡检可省 |
| 中（2–3 条线） | 总览 + 巡检 + 每条线 1 个执行 agent |
| 大（4 条线以上，有服务器、有硬件） | 总览 + 巡检 + 4–5 个执行 agent + 远端执行端 + 交互式 agent |

**宁少勿多。** 实践中开过 9 个 agent，后来精简到 4 个常驻 + 1 个执行端：
- 互相依赖很重的两条线合并给一个 agent；
- 一次性的任务（查新、环境搭建）做完就撤销，结果留在仓库；
- 暂时用不上的（如论文写作）先暂停，需要时再叫醒，靠 STATE.md 接上。

**每个执行 agent 要有清楚的边界**：写在它的提示词里——"只改哪些目录"。两个 agent 改同一个文件是冲突的主要来源。

## 3. 例子

### 例 1：机器人方向研究（原型项目，4 个常驻）

| agent | 运行方式 | 负责 |
|---|---|---|
| 总览 + 总览巡检 | 交互 + 本机定时 | 路线、决策、协调 |
| 仿真诊断 | 云端定时 | 仿真实验设计、诊断、给执行端写指示 |
| 校准与执行 | 云端定时 | 校准方法、预注册、正式实验 |
| 语言 | 本机定时 | 规格、标注、编译器评测（数据只在本机，API 密钥在本机） |
| 真机 | 交互 | 硬件、标定、真机实验（你在实验室时开） |
| 超算执行端 | 服务器上的 Claude Code | 按编号指示提交作业、贴回原始输出 |

### 例 2：毕业论文（数据分析类，2 个常驻）

| agent | 运行方式 | 负责 |
|---|---|---|
| 总览 | 交互 | 研究问题、章节结构、决策 |
| 分析 | 云端定时 | 数据清洗、统计分析、图表 |
| 写作（按需） | 交互 | 某一章写完后再开 |

### 例 3：软件项目（3 个常驻）

| agent | 运行方式 | 负责 |
|---|---|---|
| 总览 + 巡检 | 交互 + 定时 | 需求、架构决策、发布计划 |
| 后端 | 云端定时 | API、数据库 |
| 前端 | 云端定时 | 界面 |
| 测试（按需） | 云端定时 | 集成测试、回归 |

## 4. 云端还是本机

| 选云端 | 选本机 |
|---|---|
| 所有输入都在 Git 仓库里 | 要读写不进 Git 的文件（大数据、隐私数据、本机标注表） |
| 不需要你电脑上的密钥 | 要调用只配在本机的 API |
| 希望你关机时也能跑 | 能接受你开机时才跑 |

本机 agent 的限制见 [05 自动运行](05_自动运行.md) 和 [07 踩坑记录](07_踩坑记录.md)：要在桌面 app 里授权文件夹；被别的任务叫醒时拿不到电脑权限；你关机或切到另一个系统时它会跳过。
